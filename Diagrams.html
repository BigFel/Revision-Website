Different Types of Diagrams

Hope this helps you understand the different types of diagrams used in software development.

Context Diagrams (Level 0 DFD)

A Context Diagram is the highest level view of a system. It represents the entire system as a single process (a circle) and focuses on how the system interacts with external entities.

Purpose: To define the scope of the system and its boundaries.

Key Elements:

  • System: A single circle representing the whole application.
  • External Entities: Objects or people outside the system that interact with it.
  • Data Flows: Arrows showing how data moves between the system and external entities.

Data Flow Diagrams (DFD)

Data Flow Diagrams describe the logical path that data takes through a system. Unlike a map with a timetable, a DFD shows the "tracks" (paths) but not the timing or sequence of events.

Purpose: To model how data is transformed by processes and where it is stored.

Levels: They move from a general view (Level 1) to highly detailed views (Level 2, 3, etc.) using a "topdown" design.

Key Elements:

  • Processes: Circles (labeled with verbs) that transform incoming data into outgoing data.
  • Data Stores: Open rectangles representing where data sits at rest (files or databases).
  • Data Flows: Arrows showing the movement of data.

Structure Charts

Structure Charts model the hierarchy and "flow of control" within a program. They represent the architecture of the code itself by showing how subroutines (functions/procedures) call one another.

Purpose: To serve as a template for writing source code and allocating tasks to programmers.

Key Elements:

  • Rectangles: Represent subroutines or modules.
  • Call Lines: Lines connecting modules to show which subroutine "calls" another.
  • Data Flows: Arrows showing how data moves between the system and external entities.
  • Data Couples: Open circles with arrows showing data being passed.
  • Control Parameters (Flags): Filled circles showing signals that change the flow of the program (e.g., a "Found" flag).
  • Decisions & Repetitions: Diamonds represent conditional calls; circular arrows represent loops.

Data Dictionary

A Data Dictionary is a centralised repository (usually a table) that provides metadata about every variable and data structure used in a system.

Purpose: To ensure consistency across a development team and assist in future maintenance.

Common Fields:Variable name, Data type (e.g., Integer, String), Storage size (bytes), Validation rules (e.g., Age must be > 0), and Scope (Local vs. Global).

Storyboards

Storyboards are visual representations of the User Interface (UI). They combine screen designs with a navigation map.

Purpose: To document the user's experience and the navigation paths between different parts of the software.

Key Elements:

  • Screen Designs: Mockups of what the user sees.
  • Navigation Map: A diagram of rectangles (screens) and arrows showing how a user moves from one screen to another (e.g., clicking "Home" to leave a "Products" page).

Decision Trees and Tables

These tools are used to model complex logic and business rules within a system.

Decision Trees: Visual representations of decision points and their outcomes.

Decision Tables: Tabular representations of conditions and actions in a system.

Class Diagram

Specific to the Object Oriented Programming (OOP) paradigm, these diagrams describe the structure of a system by showing its classes, their attributes, methods, and the relationships between objects.

Purpose: To provide a static blueprint of the software's structure.

Key Elements:

  • Class Box: A three-part rectangle containing the Class Name, Attributes (data), and Methods (actions).
  • Attributes: The variables or data stored within a class (e.g., Price, Username).
  • Methods: The functions or behaviors a class can perform (e.g., CalculateTotal(), Login()).
  • Relationships: Lines showing how classes interact or inherit properties from one another.
